# ADR AC-1 — SOPHIA Chat through managed AgentCore Gateway

Date: 2026-10-10. Status: accepted for LOCAL implementation; no deployment.

## Decision

Use an AWS IAM-authenticated Bedrock AgentCore Gateway and one private Lambda
target. Reuse the backend's `ToolContext`, registry, Policy, Executor, audit and
model-result projection. Do not deploy the local XOC-MCP laboratory, L6 supervisor,
fixture identity, fixture signing key, or stdio diagnostic code.

The MCP laboratory remains a separate, unchanged acceptance reference. This
choice does not claim that its historical stdio teardown issue has been fixed.

Flow:

```text
authenticated POST /chat + owned AgentSession
  -> external SOPHIA runtime (unchanged)
  -> structured tool_request
  -> XOC preflight Policy + trusted ToolContext
  -> dedicated KMS GenerateMac
  -> SigV4 tools/call to fixed AgentCore Gateway
  -> private Lambda: VerifyMac + deadline + canonical Policy/Executor
  -> bounded READ_ONLY DynamoDB adapters
  -> canonical sanitized ToolResult
  -> XOC validates response/request/tool binding
  -> one controlled SOPHIA result turn
```

No tool discovery supplied by the model; four fixed name mappings only. No runtime
endpoint selection, credential passthrough, user JWT to AgentCore, recursive
tools, sampling, elicitation, multi-round-trip requests or fallback.

## Protocol and current documentation

AgentCore uses MCP **2026-07-28**, the explicitly stateless version in the current
[AWS Gateway guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-using.html).
The version appears in both header and `params._meta`; request-metadata headers
match the body. No `initialize` is sent for this version. Client capabilities are
empty. The older protocol used by the LOCAL MCP acceptance harness is unchanged.

[AWS's calls documentation](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-using-mcp-call.html)
supports direct HTTP invocation; existing requests + botocore SigV4 are sufficient.
There is no new MCP/AgentCore SDK dependency. A non-JSON/session/interim response
is unavailable, never a reason to retry or silently negotiate another protocol.
AC-2 must verify protocol availability in the actual region/account.

Lambda is supported as a [Gateway target](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-add-target-lambda.html).
Its event contains the schema properties; its client context carries the prefixed
tool name and Gateway ID. These metadata are checked but are NOT human authority.
Only the verified assertion yields `ToolContext`.

Rejected alternatives:

- API Gateway target: adds another API surface and IAM/auth wiring without solving
  an unmet requirement; the Lambda event can already carry the opaque assertion.
- AgentCore Runtime/custom container: adds image distribution, runtime/session
  operations and packaging while the target only needs bounded synchronous reads.
- Shared HS256 JWT secret: the target must not gain the ability to mint user or
  agent credentials. No changes to existing HS256 material in this task.
- Public JWT-authorized Gateway: requires new public issuer/lifecycle integration;
  only the existing trusted AWS backend needs to invoke this target.
- Direct DynamoDB/tool fallback: explicitly forbidden and not implemented.

## Authenticated context

`agentcore_context.py` encodes canonical JSON plus an HMAC-SHA256 MAC generated by
a dedicated, non-exportable KMS HMAC key. This is a **MAC**, not an asymmetric JWT.
[KMS separates GenerateMac and VerifyMac permissions](https://docs.aws.amazon.com/kms/latest/developerguide/hmac.html),
so the target can verify without permission to generate assertions.

Claims: version, audience=exact Gateway ARN, full canonical ToolContext,
tool name, SHA256(canonical arguments), issued-at milliseconds and deadline.
The context preserves actor user, role, tenant, effective tenant, delegation,
request ID and source=sophia_chat. The key ARN is trusted configuration, never a
claim or model field. Validity is at most five seconds and cannot outlive the
client's reserved tool budget. There is no clock-skew extension. Key material is
never exported, checked into Git, put in environment variables or sent to SOPHIA.

Identity comes from existing authenticated Chat and owned AgentSession. The
original thread-validation and C.3 confirmation paths are untouched. The
assertion binds the already-authorized execution request; it is not a user login
token and does not grant access to other APIs.

The target still enforces the existing registry and role policy. ADMIN and USER
retain existing READ_ONLY policy; ADMIN_XOC requires effective delegated tenant;
SUPERADMIN is denied. Context validation additionally rejects inconsistent
non-delegated tenant identity, invalid types and non-Chat sources. Model-supplied
ownership is never promoted into claims, including fields named assertion.

No distributed replay ledger is added: reads can be replayed by a party that has
both invocation credentials and the exact assertion within its <=5-second window.
The client performs no retries and never replays automatically. This is not an
exactly-once execution guarantee. WRITE tools remain excluded; introducing them
would require a separate replay/idempotency design and human confirmation.

## Data plane and IAM boundaries

Serverless Framework v3 remains the only IaC framework. New `serverless.agentcore.js`
uses the existing `buildService` pattern with a **separate explicit role** and
minimal environment. It removes the common DEV wildcard SSM grant from this
stack. No RDS URL, database secret, JWT secret, VPC or internet-facing API is
configured for the target.

| Principal | New permission | Scope |
|---|---|---|
| Existing Chat role, opt-in only | InvokeGateway | Exact Gateway output ARN |
| Existing Chat role, opt-in only | GenerateMac | Exact dedicated KMS key |
| Gateway service role | InvokeFunction | Exact read-target function ARN |
| Read-target Lambda role | VerifyMac | Exact dedicated KMS key |
| Read-target Lambda role | GetItem | Exact tickets table |
| Read-target Lambda role | Query | Exact three tables and required StatusIndex / UserStatusCreatedAtIndex ARNs |
| Read-target Lambda role | CreateLogStream, PutLogEvents | Only its own log group streams |

The target has no Sign/GenerateMac, SSM, Secrets Manager, RDS, table writers,
Scan, Lambda invoke, Step Functions, S3 or EventBridge permission.

Intentional wildcard explanations:

- KMS **key policy** Resource `*` denotes that policy's single attached key, not
  all account keys. Explicit management/data action names delegate to account IAM;
  runtime identity policies grant only their one required MAC operation.
- Gateway role trust constrains account, region and `${gateway-name}-*` because
  AWS generates the suffix; directly referencing Gateway ARN in its own required
  role would introduce a CloudFormation creation cycle. No wildcard invocation
  resource is used. SourceAccount prevents another account assuming that role.
- Log ARN `...:log-group:/aws/lambda/<exact-function>:*` covers only generated log
  stream names. CloudFormation creates the log group; no CreateLogGroup grant.

The gateway and target are same-account; the service role's identity policy is
sufficient for Lambda invocation, without a public Lambda resource policy. See
[AWS permissions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-prerequisites-permissions.html).

Chat's pre-existing broad DEV grants are NOT expanded or cleaned up here. Chat
and Voice currently share a Lambda execution role in this repo; opting in adds
permissions to that existing trusted process, not a new isolated Chat principal.
No Voice path is wired to the client. This distinction must not be represented as
new process-level isolation from code already running in the same Lambda.

## Providers and budgets

`ReadOnlyProviders` uses existing key builders/serializers and the Executor's
argument validators. It does not replace/mutate shared store modules, enable
local-file stores, or call existing ticket helpers that scan all pages without
a deadline. Only the four target handler bindings use these bounded adapters.

Ticket get uses the tenant partition plus ticket ID, never the global lookup
index. List/status keys remain those of existing tables. Unread count binds both
tenant and user. Pagination checks budget each page and caps at 20 pages; overflow
is unavailable, never a partial count presented as complete. Reports can return
the requested bounded list. Default list limit 50, maximum 200, model projection
up to 50 as in the canonical formatter.

Chat Lambda stays 20 seconds; governed Chat deadline stays 18. AgentCore execution
has at most five seconds and reserves at least two seconds for the second model
turn. KMS/DynamoDB clients have short connect/read timeouts and one attempt.
Target Lambda timeout is five seconds with reserved concurrency four. No provisioned
concurrency, queue, persistent custom supervisor or account changes in AC-1.

Absolute application deadlines are checked around calls and while consuming the
response, but synchronous DNS/OS/credential resolution may overshoot a wall-clock
budget before returning. The Lambda hard timeout remains the last bound; AC-2
must measure real cold starts, DNS, KMS and Gateway latency. This is not a proven
production latency SLA.

## Rollback / activation

Without `SOPHIA_AGENTCORE_PROVISIONED=true`, Chat's Serverless configuration keeps
the previous behavior and does not resolve AgentCore outputs. Provisioning refs
is separate from activation: the opted-in template defaults
`SOPHIA_TOOL_EXECUTION=disabled`, returning unavailable for tools.

Explicit `agentcore` selection requires governed Chat. Unknown/disabled modes
deny. AgentCore takes precedence over the LOCAL harness seam and never invokes
LocalMCPExecution/direct ToolExecutor after an error. Default legacy `direct`
composition remains only for the non-migrated deployment; it is not an automatic
recovery mechanism. Roll back activation to `disabled`, not a hidden direct fallback.
